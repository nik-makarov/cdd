# Releases

## Automatic versions

Pushes to `main` run Linux/macOS checks and the vulnerability audit before
publication, except when every changed path is a Markdown file (`**/*.md`) or
under `docs/`. Such documentation-only pushes skip the Release workflow entirely
and create no tag, release, or tap update. Documentation is included in the next
release that changes another path. A mixed code/documentation push still releases.
Pull-request CI and scheduled audits are unaffected.

Only successful checks allow publication. One eligible push releases its final
commit, even when it contains several commits. Pull requests, weekly audits,
dependency-update branches, and tag pushes do not publish releases.

The first release is `v0.1.0`, from the base in [VERSION](../VERSION). Later pushes
increment the highest stable tag's patch number: `v0.1.1`, `v0.1.2`, and so on.
Change VERSION to a higher base such as `0.2.0` to start a new minor series. The
file is a floor, not a counter; no version-bump commits are generated by CI.
Use SemVer: patch for compatible fixes, minor for compatible new behavior, and
major for incompatible shell, argument, output, or exit-code contracts.

Publication runs are queued without canceling the active run. GitHub's queue
supports up to 100 pending runs; within a push only its final commit is released.
The latest release must be an ancestor of the commit being published. An old or
rewritten branch cannot publish over a newer release. Retrying the latest tagged
commit reuses its tag and completes unfinished publication or tap delivery.
Do not retry an older run after a newer commit has been released.

CI creates tags and publishes releases; no manual Release button or local tag
is needed. Do not edit or replace a published tag or release asset.

## Supported archives

| Operating system | Architecture | Filename suffix |
| --- | --- | --- |
| Linux | x64 / amd64 | `linux_amd64.tar.gz` |
| Linux | arm64 | `linux_arm64.tar.gz` |
| macOS | Intel / amd64 | `darwin_amd64.tar.gz` |
| macOS | Apple Silicon / arm64 | `darwin_arm64.tar.gz` |

Each binary archive contains `cdd`, standalone instructions, the MIT LICENSE,
THIRD_PARTY_LICENSES.txt, and version-specific RELEASE_NOTES.md. GitHub Releases
also contain a committed-source archive, SHA256SUMS for all five archives, and
the generated `cdd.rb` formula. The source archive includes only the committed
Git tree and has deterministic metadata and compression. It contains no local
build products or `.git` directory.

No Go installation is needed to use a prebuilt executable. The workflow does
not sign or notarize binaries. The Homebrew formula builds from source instead.

## Homebrew

After the first release:

```sh
brew install nik-makarov/tap/cdd
eval "$("$(brew --prefix)/bin/cdd" --init zsh)"
```

Add the initialization line to `~/.zshrc`, or use `--init bash` in `~/.bashrc`.
Homebrew installs Go as a build dependency, downloads the exact versioned source
archive, verifies SHA-256, and builds with the release version embedded. Licenses
are installed under the package's shared data directory. No Developer ID or
notarization is needed for this source-build route.

The generated function records the absolute executable path, which may refer to
Homebrew's versioned Cellar. After `brew upgrade cdd`, rerun the initialization
line in existing shells; new shells initialize the installed version automatically.

### Initial setup

1. Push the bootstrap `nik-makarov/homebrew-tap` repository's `main` branch first.
   It intentionally has no formula until the first successful cdd release.
2. Create a fine-grained personal access token restricted to
   `nik-makarov/homebrew-tap`, with **Contents: read and write**. Save it as the
   `HOMEBREW_TAP_TOKEN` Actions secret in `nik-makarov/cdd`. Never commit the token.
   Use an expiry date and rotate the secret before it expires.
3. Allow the cdd workflow to create tags/releases, and the token's owner to push
   formula updates directly to the tap's main branch. Repository rules that
   require PRs or restrict tag creation need an explicit compatible configuration.
4. Push cdd's `main`. Inspect its Release workflow and the subsequent tap checks.

The built-in GITHUB_TOKEN is used only for cdd's tags and releases. The separate
tap token is exposed only to the credential check and tap update steps. It does
not need Actions or workflow-file write permission. A GitHub App installation
with equivalent tap access can replace it later.

The bootstrap tap's first workflow checks structure only. Publication adds its
first formula; that commit triggers style checks, a source build, and formula
tests on macOS. No Homebrew bottles or GoReleaser dependency are required.

### Publication and recovery

After checks, the Release workflow:

1. Validates tap credentials and chooses or reuses the release version.
2. Builds four binaries, source archive, notes, SHA-256 checksums, and formula.
3. Pushes the tag for the exact checked commit.
4. Creates or resumes a draft release, uploads assets, and publishes it.
5. Downloads the published formula and commits only Formula/cdd.rb to the tap.

An already published release is never rebuilt or overwritten on a retry. If tap
updating fails after publication, fix access or repository rules and rerun the
latest Release job; it will reuse the published formula. Unrelated tap files are
preserved. A conflicting tap push fails rather than forcing or overwriting history.

## Release notes

The first release uses the curated Unreleased section in CHANGELOG.md. Later
releases list the English commit subjects since the previous stable tag, with a
comparison link. Write subjects that explain the resulting behavior; do not use
Conventional Commits prefixes. A matching dated CHANGELOG section overrides the
automatic notes when a release needs a more polished explanation:

```markdown
## v0.2.0 - 2026-11-13

### Added

- Describe the improvement for users.
```

Use the actual release date. An explicit section must be unique, dated, and
nonempty; invalid curated notes fail publication rather than falling back.
The local CHANGELOG is maintained editorially and is not rewritten by the bot.
GitHub Releases are the complete chronological history of automatic versions.
The development journal records implementation and verification separately.

## Use an archive

Download the matching binary archive and SHA256SUMS from the same GitHub Release.
For example, after substituting an available version:

```sh
shasum -a 256 cdd_vX.Y.Z_linux_amd64.tar.gz
```

Compare with the entry for that exact filename. Extract into an empty directory:

```sh
tar -xzf cdd_vX.Y.Z_linux_amd64.tar.gz
eval "$(./cdd --init zsh)"
cdd
```

For bash, use `--init bash`. Put the executable in a permanent location before
adding initialization to shell startup files. See [usage](usage.md).

## Local previews

```sh
make dist
```

This writes four binary previews under `dist/dev/` using Unreleased notes.
For a manually curated versioned preview, prepare the matching CHANGELOG section
and run `make dist VERSION=vX.Y.Z`.

To reproduce the automatic packaging route from a clean committed checkout:

```sh
version="$(go -C tools run ./release -root .. -next-version)"
make dist VERSION="$version" RELEASE_FLAGS=-automatic
```

The second form also generates source, formula, and automatic notes. It refuses
uncommitted source changes. Both forms are local previews: they create no tags,
releases, tap updates, or remote changes. Generated files are ignored by Git.
